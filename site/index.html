Put the runtime back
in infrastructure.

Like the OS or Kubernetes, the runtime is provisioned and updated as infrastructure—not rebuilt into each application image.

A conventional application image

The application image references its runtime and userland. Updating that base normally means rebuilding or recomposing the application image, then rolling it out.

Application + dependenciesRuntimeOS userland

With Brewlet

The workload ships code, dependencies and a launch descriptor. Infrastructure supplies and updates the approved runtime. New containers use the updated runtime without rebuilding application bytes.

Application + dependencies + launchInfrastructure: runtime + userland

Both approaches cache unchanged layers. Shared runtime files do not mean shared application processes or heaps. Runtime rotation does not patch libraries bundled in your application.

Built around Kubernetes.
Not another workload API.

Applications declare an approved runtime ID. Kubernetes schedules the workload; Brewlet supplies the runtime from the node.

  1. Approve the runtime

    A cluster-scoped RuntimeImage binds a stable ID to a digest-pinned image and non-root account. A NodeProfile offers it on selected pools.

  2. Publish the application

    Package explicit app/dependency layers under /app, a versioned launch.json and declared OCI platforms. The CLI never guesses the language.

  3. Select, schedule, compose

    Use a normal Deployment with runtimeClassName: brewlet and one runtime ID. The shim validates the artifact, leases a runtime generation and delegates to runc.

Installed when you need it.

Choose Eager for a warm pool, or OnDemand to validate baseline readiness before fetching runtime roots. A bounded first-use wait lets kubelet retry installation without running unvalidated application code.

A process, not a language plugin.

Describe what to execute. Declare what to package. The runtime ID remains an explicit choice in your workload.

launch.json
{
  "schemaVersion": 2,
  "process": {
    "entrypoint": ["python3"],
    "args": ["/app/src/main.py"],
    "workingDir": "/app"
  }
}
Package and publish
brewlet push registry.example.com/apps/api:v2 \
  --platform linux/arm64 \
  --launch launch.json \
  --layer app=./src:/app/src

This example has no third-party dependencies. Add explicit dependency layers and lookup paths when your application needs them.

Examples are templates, not a live terminal. Use your registry and actual supported platforms. Java project intelligence is available in the optional Maven producer; it does not select a pod runtime or generate workloads.

Your workload still looks like Kubernetes.

Keep Services, probes, resources, volumes and normal rollout strategies. Each application container in a Brewlet Pod uses the same runtime ID.

Patch the runtime.
Keep the application.

Rotate the digest behind a stable runtime ID. New containers resolve the approved current generation. Existing containers keep a durable lease on the generation they started with.

Optional, opt-in workload restarts use an inventory-epoch and minimum-generation barrier. A successful template patch is not a completed remediation.

A few important
distinctions.

Can I bring my own custom runtimes?

Yes. Use a compatible upstream image unchanged, including distroless images, or build your own OCI runtime image. Approve its digest as a RuntimeImage, offer it through a NodeProfile, and select its ID in your workloads. The runtime image contract requires validated platforms and non-root numeric identities, not a shell or an account named app. Use explicit executable paths when the runtime has no PATH.

Do existing applications switch runtime in place?

No. Running processes keep their leased generation. New containers use current. An optional restart coordinator can patch opted-in native controllers; it does not hot-swap a VM, kill pods directly or override rollout strategies.

Do I still need an application image?

Yes. The application is a standard, digest-addressed OCI image with application layers, optional dependency layers and a final launch layer. It omits the platform runtime root; it is not an image-free deployment.

Does sharing the runtime mean sharing processes?

No. Runtime files are shared read-only on the node. Every workload has its own process, resources and container isolation. There is no claim of automatic heap sharing or benchmarked memory savings.

Can I use ordinary images and run as root?

Ordinary workloads still use the stock Kubernetes runtime. Within a Brewlet Pod, every application container must use a v2 artifact and run non-root without privilege escalation. Only the infrastructure sandbox bypasses application processing.

What changes from main?

RuntimeImage replaces JDK-specific approval, launch.json replaces JVMConfig, and native Kubernetes workloads replace JavaApplication. The CLI is intentionally generic. See the side-by-side comparison and equivalent workflows.
