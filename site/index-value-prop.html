Automated container delivery

A fair baseline: Jib or buildpacks, reusable layers, centralized pipelines, and admission policy.

  1. Approve the runtime update.Review the source and qualify application compatibility.
  2. Produce updated application images.Reuse compiled code and unchanged layers where possible. Each changed image gets a new digest.
  3. Publish and update release evidence.Refresh digest-bound signatures and attestations as your policy requires.
  4. Roll out and confirm adoption.Replace workloads and verify that the intended runtime is running.

Application and runtime, separated

The application image remains immutable. The approved runtime changes through the platform.

  1. Approve the runtime update.The same review and compatibility responsibilities apply.
  2. Update the node runtime sources.Apply reviewed JDK source digests to the relevant node pools.
  3. Keep application images unchanged.No runtime-only application-image publication. Record and approve the runtime change separately.
  4. Roll out and confirm adoption.Restart workloads after nodes are ready. Running JVMs are not patched in place.

The restarts remain.
The runtime-only application-image publication work does not.

What about Jib, buildpacks, and rebasing?

Jib already provides Dockerfile-free, daemonless Java image publication. Buildpack rebasing replaces run-image layers without rebuilding application layers, but still changes the application image digest. In standard Paketo Java images, the JRE is a buildpack launch layer, so a base-only rebase does not update that JVM. An updated image can be built from a precompiled application. Brewlet's distinction is independent runtime maintenance, not exclusive access to efficient image tooling.

A smaller delivery contract.
Still Kubernetes.

Keep your application code and dependencies in the application lifecycle. Move JDK selection and maintenance into the platform lifecycle. Publish once, then deploy the same application digest to compatible, prepared nodes.

Follow the developer workflow  →
1Build your Java application.
Use your normal Maven build. Brewlet supports executable JARs, layered classpaths, and JPMS modules.
2Publish through the Maven plugin.
Ship application bytes and launch metadata to an OCI registry. The platform supplies the JDK and its userland.
3Declare the workload.
A JavaApplication describes the image digest, Java requirements, resources, and probes. Its controller manages the Deployment, Service, and optional HPA.
4Operate with familiar tools.
Keep Kubernetes networking, logs, exec, and workload rollouts. The Brewlet runtime uses runc isolation and pod resource limits.

Make the approved path explicit.

Security responsibilities do not disappear. Brewlet gives platform and application teams distinct places to exercise them.

Approve runtime sources centrally.
NodeProfile resources select node pools and digest-pinned JDK sources. New launches select from the node's active runtime inventory. Runtime management
Verify dependency composition.
Managed dependency bundles compare the complete resolved Maven runtime graph with an approved lock, including JAR digests. Publication reuses the verified classpath layer. Managed bundles
Enforce trusted publication.
The optional Ratify/Gatekeeper integration requires a trusted final-image managed-dependency attestation. It needs configured keys, policy, and an OCI Referrers-API registry; it is not automatic or general-purpose signature admission. Admission enforcement
Audit the complete environment.
Review application and runtime evidence together, not just the application image. Node inventory reports installed JDK builds; automatic per-replica runtime reporting remains planned work.

Dependency updates still require new application images. Managed mode requires thin JARs. Brewlet retains container-grade isolation; it is not a stronger hostile-tenant sandbox. Read the security and privileged-provisioning model.

Better operations.
Not a faster-Java claim.

The goal is simpler delivery and more governable change. Performance must be no worse than conventional container deployments. That is an acceptance requirement, not a result Brewlet has already established.

A recorded PetClinic experiment showed similar warm startup, but approximately 21% higher sampled JVM-plus-shim PSS with Brewlet. The runtime stacks used different containerd and Go builds; sustained throughput, tail latency, and cold deployment were not measured.

What needs attention in an evaluation?

Brewlet is a pre-1.0 preview. Use a disposable evaluation environment. Privileged node provisioning adds platform responsibilities. Current capability admission does not support waking a completely zero-sized pool; missing node identities can block profile cleanup and upgrades. Ordinary-image ephemeral debug containers are not supported. Review node lifecycle constraints and workload operations before adoption.
